You are a senior full-stack TypeScript engineer, browser automation specialist, accessibility engineer, product designer and application security engineer.

**Product:** Buggd
**Tagline:** Find what's broken.

## PRIMARY OBJECTIVE

Transform Buggd from a technically capable website scanner into an exceptionally intuitive website testing and improvement tool that ordinary website owners, designers and non-technical users can understand.

The user should finish a scan knowing:

1. What needs attention.
2. Whether an issue is definitely broken or merely suspected.
3. Exactly which page and element is affected.
4. Why the issue matters.
5. What to do to resolve it.
6. Whether their subsequent changes actually fixed it.

**Buggd must move from "Here are your technical findings" to "Here's what's wrong, exactly where it is, and how to put it right."**

This is a full implementation task, not a planning exercise or UI mock-up.

Implement all requirements below, including frontend, backend, scanner changes, data models, persistence, exports and automated tests.

Do not silently omit features.

# 3. INTRODUCE HUMAN-FRIENDLY REPORTING

## Current problem

Buggd currently exposes technical descriptions such as:

- Interactive control has no observed accessible name
- Custom validation and form processing not tested
- Element locator: a
- Horizontal overflow detected
- HTTP 404
- Network request failed
- No observable interaction response

These are difficult for ordinary users to interpret.

## Required improvement

Create a central, typed explanation registry for every supported detector.

Each finding type must have:

- Plain-English title
- Short explanation
- Why it matters to website visitors
- What Buggd actually observed
- Practical suggested fix
- Optional platform-specific fix
- Developer-specific technical guidance
- Confidence/evidence classification
- Relevant affected element information
- Technical detector identifier

Example transformations:

**Current:**
Interactive control has no observed accessible name

**New:**
Some buttons or links may be missing descriptions.

**Explanation:**
People using screen readers might not be able to understand what these controls do.

**Suggested fix:**
Find the highlighted control and give it a meaningful description.

---

**Current:**
HTTP 404

**New:**
This link leads to a page that doesn't exist.

**Explanation:**
Visitors clicking this link may reach an error page instead of the information they expected.

**Suggested fix:**
Update the link destination or restore the missing page.

---

**Current:**
Horizontal overflow detected

**New:**
Part of this page may be cut off on smaller screens.

**Explanation:**
Some visitors might have to scroll sideways or may be unable to see part of the content.

**Suggested fix:**
Review the highlighted section at the affected screen size and adjust its layout.

---

**Current:**
Custom validation and form processing not tested

**New:**
Contact form delivery wasn't tested.

**Explanation:**
Buggd checked the form's safe, observable behaviour but didn't submit a real enquiry. You'll need to verify that messages are successfully delivered.

This last result is a coverage limitation, not a website defect.

## Writing rules

All default explanations must:

- Use UK English.
- Avoid unnecessary technical jargon.
- Use short sentences.
- Avoid ambiguous or alarming claims.
- Explain visitor impact.
- Provide clear next actions.
- Distinguish an observed fact from an inference.
- Never promise that a proposed fix is guaranteed to work.

Explanations must be generated from actual evidence and maintained as deterministic templates.

Do not require AI APIs.

Do not generate generic advice disconnected from the actual finding.

# 5. EXACT VISUAL IDENTIFICATION OF AFFECTED ELEMENTS

**This is one of the highest-priority requirements.**

When Buggd identifies a broken link, suspicious button, unlabelled control, missing image or layout issue, the user must be able to see exactly which element is affected.

A result such as `Element locator: a` is not acceptable as the only identifying information.

## Required captured evidence

Where applicable, record:

- Page URL
- Element tag and semantic role
- Visible element text
- Accessible name or observed lack of one
- Relevant attributes
- Destination URL
- Stable or best-available locator
- Nearby identifying text
- Element bounding rectangle
- Viewport dimensions
- Device pixel ratio
- Scroll position
- Screenshot reference
- Parent region or landmark where identifiable
- Relevant interaction state

Use Playwright-supported DOM inspection, locator APIs and accessibility tooling.

## Visual highlighting

Create a visual issue-inspection experience.

When someone selects an element-specific finding:

1. Show the relevant screenshot.
2. Locate the affected element.
3. Draw a visible highlight around its actual bounds.
4. Scroll or pan the screenshot view to the issue if necessary.
5. Show an identifying label.
6. Provide a concise explanation.
7. Allow the user to navigate to another occurrence.

For example:

**Issue:** This button may be missing a description.

**Where:** Homepage → Header → Mobile menu button

**Element:** Menu icon at the top-right of the page.

The user should see that exact element highlighted in the screenshot.

## Technical accuracy

Screenshot highlights must be calculated from captured evidence.

Account for:

- Viewport size
- Screenshot dimensions
- Scroll offsets
- Device pixel ratio
- Screenshot scaling
- Full-page versus viewport screenshots
- Responsive viewports
- Fixed and sticky elements
- Elements that moved or disappeared
- Browser-rendering differences

Support iframe and shadow-DOM elements where technically practical, while accurately documenting limitations.

Prefer capturing element-level evidence or annotated viewport screenshots when that offers more reliable positioning.

**Never guess element coordinates or draw a highlight unrelated to the actual detected element.**

If highlighting is unreliable, show the unannotated screenshot and explain that the element could not be precisely located.

## Required inspector controls

- Highlight affected element
- Previous occurrence
- Next occurrence
- View affected page
- Open live website
- Copy element details
- Expand technical information

Do not invent a direct deep link to an arbitrary element when one cannot be generated reliably.

# 8. REORGANISE RESULTS INTO THREE CLEAR CATEGORIES

## A. Problems found

- Broken internal link

## B. Things to check

- Real form submission
- Payment processing
- Authenticated account workflow
- Blocked third-party resource

**Checks not performed must not count as website problems.**

- Dashboard summary
- Issue list
- Sidebar counts
- Filters

- Exported reports
- Guided workflow
- Scan comparisons
