## Delivery

| Area | Implemented behaviour |
| --- | --- |
| 1. Owner experience | Simple is the default. Human explanations, impact, actual observations and suggested actions replace raw detector titles. The cream/olive/lime theme, fonts, rounded cards and vector identity are preserved. |
| 2. Detection engine | Unique DOM locators, explicit source evidence, per-rule/per-viewport coverage, resource provenance and bounded additional captures extend the existing real Chromium crawler. Real safe interactions, native form checks, cancellation, SSE, map, history and deletion remain operational. |
| 3. Reporting/classification | A central typed registry covers all current detector families. Confirmed problems, potential issues and checks not performed are separate from severity. Unperformed checks do not contribute to website-problem counts or resolved-problem comparisons. |
| 4. Element highlighting | Captured tag/role/text/name/attributes/URL/region/fragment/rectangle/viewport/DPR/scroll/state and screenshot IDs drive actual overlays. CSS-scale PNG dimensions and before/after measurements establish alignment. Moved, missing, unmatched and legacy evidence gets an explicit unannotated fallback. Zoom, highlight toggle, occurrence navigation, affected-page inspection and live-page links work. |
| 5. Grouping | Fingerprints use rule, confidence, full element identity/destination/region or equivalent resource evidence. Distinct sibling controls do not merge merely because they have the same tag. Cross-page shared components are suggested cautiously. Individual places and repeated-event counts remain available. Located image evidence enriches the original HTTP event instead of duplicating a place. |
| 6. Guided fixing | Six real steps cover selection, location, impact, platform guidance, review and rescan. Previous/next/skip, mobile step navigation and keyboard controls work. Platform, selected issue, current step, review status and dismissal reason persist locally in a separate workspace. |
| 7. Scan comparison | Linked rescans and explicit previous-scan selection work for the same origin. Comparisons distinguish resolved, remaining, new and unable to verify, with reasons and previous/current evidence. Verification requires the affected page, relevant rule/screen size, a sufficient identity match and successful coverage. Interaction/form verification requires that particular element's check. Failed/cancelled/skipped/blocked or structurally ambiguous absence is not a fix. HTML and JSON comparisons export locally. |
| 8. Platforms | WordPress, Webflow, Framer, Squarespace, HTML/CSS/JavaScript, React/Next.js and AI-built/unsure guidance uses deterministic templates. Platform overrides persist per scan. Copyable assistant prompts contain actual evidence and explicitly avoid invented source files or causes. |
| 9. Exports | Standalone scriptless HTML, offline Chromium PDF and structured JSON contain real scan data. Owner reports include summary, priorities, confidence categories, fixes, limitations, captured evidence and a technical appendix. Accurate close-ups use verified bounds. Embedded PNG definitions are reused, so repeated findings cannot multiply the image-byte budget. JSON retains original observations plus a separate workspace; known secret/path redaction applies only to shared output. PDF failures offer recovery instead of downloading an error as a PDF. |
| 10. Accessibility accuracy | dom-accessibility-api replaces the text-only name heuristic. Fixtures cover named/unnamed icons, SVG titles, image links, hidden references, visually hidden text, nested content, decorative controls, responsive states and open shadow roots. SVG titles no longer count as duplicate document titles. Explicit presentation/hidden images do not receive missing-alt findings solely for an omitted attribute. |

Scanner data, deterministic presentation, human review and verification remain separate. A manual **Fix attempted** status never means the scanner verified a fix. The original observations are not rewritten when changing display mode or review progress. Optional v1.1 model fields and fallback presentation keep older completed scans readable.

## Limits and incomplete acceptance gates

No requested application stage has been intentionally deferred. The following scope limits and release-validation gates remain explicit:

- **Not a comprehensive audit.** Accessible names and geometry checks cover supported patterns, not complete WCAG, visual, SEO, security or visitor-journey correctness. Custom handlers, real enquiries/payments, authentication, clipboard/browser UI and delayed effects require authorised manual checks.
- **Iframe/closed-shadow coverage.** Open shadow DOM is supported for naming/evidence. Iframe contents and closed shadow roots are not inspected. No element coordinates are invented for inaccessible content.
- **Bounded evidence.** Captures are viewport-based at 1440/768/390px, with bounded additional offscreen/action images. Fixed/sticky elements use the actual captured viewport. Full-page capture is not enabled. Very long pages, lazy states, changing content and budget exhaustion may prevent exact evidence; fallbacks explain this.
- **Bounded exports.** Ten unique captures and 12 MiB of image data; PDF first 100 prioritised groups, one renderer at a time, bounded output and timeouts. HTML/JSON preserve additional findings. PDFs are print-friendly but are not claimed to be PDF/UA-tagged accessible documents.
- **Resource policy.** Default external blocking can change rendering. Explicit public assets are anonymous, bounded GETs for eligible image/font/style/script resources, with public-IP validation per redirect and no forwarded credentials or Set-Cookie. External pages/APIs/private destinations/writes remain blocked. A completeness flag describes observed capture conditions, not exhaustive successful loading.
- **Conservative verification.** DOM replacements, changed identity, missing pages/checks or rendering interference can remain unable to verify even after a real fix. This is deliberate uncertainty, not a failure to save review progress.
- **Privacy.** Known credential/path patterns are redacted and explicit form values excluded from element fragments. Screenshots and visible site content can still contain private information. Review reports before sharing; redaction is not an exhaustive personal-data detector.
- **Original saved-site site.** No specific authorised saved-site URL was supplied in this request. The reported class of repeated accessible-name/resource findings was retested with representative real-browser fixtures; this is not a claim of a fresh saved-site production audit.
- **Platform release validation.** Linux Node 22/24 CI and Windows install/start/browser/shutdown testing still require actual runs. Local macOS success is not evidence those platforms passed. Wider real HTTPS/CDN/builder samples and assistive-technology review remain advisable.
- **Brand source.** Runtime logos are reusable path-based SVGs with theme-aware components. The approved board remains a reference. Exact designer vector masters were unavailable; the existing close reconstruction is preserved for owner review.
- **Publication.** The package remains private and unpublished. Registry ownership, provenance, public `npx buggd`, deployment and GitHub release status are not claimed. Nothing has been pushed, published or deployed externally.

## Before a public release

1. Review this candidate, screenshots, sample reports, security notes and reconstructed vectors.
2. Run Linux CI and Windows/manual checks, plus representative authorised real-world sites and assistive-technology review.
3. Review dependencies/licences, npm name ownership, provenance and final release metadata.
4. Obtain explicit approval before pushing, publishing or deploying. Keep the private-package safeguard until that release is approved.
